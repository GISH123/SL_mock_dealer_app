Mock Dealer App - DT/BAC Control 用户手册

简体中文版 · 浏览器可直接打开阅读 · 适用于当前最终版 Mock Dealer App 与对应 pydealerLight 控制流程

1. 文档目的

本文用于说明 Mock Dealer App 的 DT / BAC 控制界面 如何使用，尤其是：

  • DT（3 slots） 与 BAC Classic（6 slots） 的区别
  • Auto Dispatch 与 Dispatch All (burst) 的实际工作方式
  • 测试时应该按哪些按钮、按什么顺序按、以及每个按钮的用途

2. 模式说明

模式 格数 说明
DT (3 slots) 3 用于 DragonTiger / DT 类三格流程。界面中会显示 3 个 index，常见顺序为 1 → 3 → 2。
BAC Classic (6 slots) 6 用于经典 BAC 六格流程。界面中会显示 6 个 index。

3. 启动后的界面含义

主界面顶部蓝色文字会显示当前状态，例如：

DT dealer connecting | control=HTTP | TCP listen 0.0.0.0:2331 | HTTP http://127.0.0.1:1234

含义如下：

  • DT dealer connecting：当前是 DT 三格模式，程序正在等待 pydealerLight / detector 端进入可工作状态。
  • control=HTTP：当前主要控制路径使用 HTTP。
  • TCP listen ...：本地 TCP 监听地址。
  • HTTP ...：当前配置的 HTTP 控制地址。

4. 主按钮用途

按钮 用途
Start New Round && Prediction 开始新一局，并向 pydealerLight 发出 start predict。通常这是一局流程的起点。
Save Result 发送保存结果指令。当前工作流中，通常先保存结果，再停止预测。
Stop Prediction 发送 stop predict，结束当前这局的预测流程。
Dispatch 1 / Dispatch 2 / ... 手动发出单个 index 的 dispatch。适合人工逐格测试。
DT_Auto Dispatch (3 slots) / BAC_Auto Dispatch 按预设顺序自动 dispatch。更适合标准测试流程。
Dispatch All (burst) 按当前顺序快速连续发送多个 dispatch。更适合 burst/manual 测试，而不是“逐格等待完成”的标准流程。
Apply 应用当前 order 设置。

5. Dispatch All (burst) 与 Auto Dispatch 的核心区别

最重要的区别：
Dispatch All (burst) 不会等待当前 index 完成后再发送下一个 dispatch index。
Auto Dispatch 会等待当前 index 完成后，才继续发送下一个 dispatch index。

5.1 Dispatch All (burst)

Dispatch All (burst) 会按照当前 order，快速连续把多个 dispatch 发出去。例如在 DT 模式下，order 为 1 → 3 → 2 时，burst 会在很短时间内连续发送：

dispatch 1 → dispatch 3 → dispatch 2

它的特点是：

  • 不会等待前一个 index 完成。
  • 更适合验证 pydealerLight 是否能同时接收和处理多个 active index。
  • 更像“快速连续触发”或“并发压力测试”。
  • 不建议把它理解成标准业务流程中的“逐格自动完成”。

5.2 Auto Dispatch

Auto Dispatch 是标准、直观、最推荐的测试方式。它会按 order 顺序逐格发送 dispatch，并且：

  • 先发送当前 index
  • 等待该 index 完成并返回有效结果
  • 再发送下一个 index
  • 所有目标 index 都完成后，再按设定的 Save gap / Stop gap / Gap 执行后续动作
简单记法：
burst = 快速连发，不等当前格完成。
auto = 逐格推进，等当前格完成后再发下一格。

6. 推荐测试方式

6.1 简单演示

  1. 启动 Mock Dealer App
  2. 选择 DT (3 slots) 或 BAC Classic (6 slots)
  3. 确认 control mode（通常为 HTTP）
  4. 等待 pydealerLight 进入可连接状态
  5. 点击 Auto Dispatch
  6. 观察界面中的卡位、日志、以及 Save / Stop 的排程

这是最接近“业务流程”的测试方式，也最方便说明给非开发人员。

6.2 如果要验证 pydealerLight 的并发 dispatch 行为

  1. 设置 order，例如 DT 常用 1 3 2
  2. 确认 Dispatch All every (s) 的数值
  3. 点击 Dispatch All (burst)
  4. 观察 pydealerLight 是否同时接受多个 active index，并分别返回结果

这种方式主要用于技术验证，不建议当成最直观的操作演示。

7. 建议的 DT 测试流程

  1. 模式选择：DT (3 slots)
  2. order：通常使用 1 3 2
  3. 点击 DT_Auto Dispatch (3 slots)
  4. 等待流程自动完成
  5. 如需人工控制，则先 点击 Start New Round && Prediction，再Dispatch index 1~3，再Save Result，再 Stop Prediction

8. 时间参数说明

参数 说明
Dispatch All every (s) burst 模式中，相邻 dispatch 之间的发送间隔。
Save gap (s) 全部目标 index 完成后，延迟多久发送 Save Result。
Stop gap (s) 全部目标 index 完成后，延迟多久发送 Stop Prediction。
Gap (s) 当前 round 结束后，到下一 round 开始前的等待时间。

9. 日志怎么看

界面下方日志区会显示当前动作与顺序。可重点关注：

  • [SEND] Dispatch ... idx=...：已经发送 dispatch
  • detected idx=... -> advance to next：当前格已完成，自动进入下一格
  • Completed order=...：本轮目标 index 已全部完成
  • SaveResult now ...：发送保存结果
  • StopPredict now ...：发送停止预测

10. 常见误解

误解 1：Dispatch All (burst) 和 Auto Dispatch 是一样的。
不是。burst 不等待当前 index 完成；auto 会等待当前 index 完成后再继续。
误解 2：Dispatch All 比 Auto 更“标准”。
不是。标准、最容易讲清楚的流程通常是 Auto Dispatch；burst 更适合技术验证。
误解 3：Save Result 和 Stop Prediction 先后顺序无所谓。
当前工作流建议：先 Save Result，再 Stop Prediction。

11. 如果只需要一句话解释：

Auto Dispatch 是“按顺序逐格测试，当前格完成后再发下一格”；
Dispatch All (burst) 是“快速连续把多个格的 dispatch 发出去，不等当前格完成”。
